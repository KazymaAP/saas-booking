## 1. Что это за проект

**«Запишись»** — SaaS: готовые сайты-визитки с онлайн-записью для малого бизнеса
(детейлинг, салоны красоты, стоматологии, фитнес, репетиторы, фотостудии, юристы,
ветклиники, клининг, ремонт техники — 10 ниш).

Две аудитории:

1. **Предприниматель** — покупает сайт: подписка 1 000 ₽/мес (домен сервиса) или
   2 500 ₽/мес (свой домен), разовый запуск 5 000 ₽, выкуп кода 5 000 ₽.
   Цены лежат в таблице `settings` (`tariffs`, `default_price`) и читаются через
   `getPricing()`; значения по умолчанию — в `общие/lib/legal.ts → DEFAULT_PRICING`.
2. **Партнёр** — продаёт те же сайты, получает 1 000 ₽/мес с подписки клиента или
   1 000 ₽ разово за продажу кода, либо 25 % от своей цены. Экономика зашита в
   `общие/lib/partners.ts → computeDeal()`.

Продажи идут через личный кабинет партнёра: партнёр создаёт счёт (`createCheckout`),
клиент открывает `/pay/[id]` и платит через ЮKassa. Публичной самостоятельной покупки нет.

Нюанс, который стоит знать сразу: вариантов счёта в коде три — `subscription_5000`,
`code_5000`, `custom`. Первый выставляет клиенту **5 000 ₽/мес**, хотя лендинг и оферта
говорят про 1 000 ₽/мес (наш домен) и 2 500 ₽/мес (свой домен). Разбор — раздел 7.2.

Прод: **https://www.zapishisya.ru** (основной домен). Репозиторий:
**https://github.com/KazymaAP/saas-booking**.

## 3. Запуск и проверки

Node 22.x (`package.json → engines`). Важно: в настройках проекта на Vercel стоит
**Node 24.x** (`.vercel/project.json → settings.nodeVersion`), то есть локально и на проде
разные версии Node. Сборка на обеих проходит, но если поведение разойдётся — смотреть сюда.

Пакетный менеджер — **pnpm**: `vercel.json` задаёт `installCommand: pnpm install` и
`buildCommand: pnpm build`, в репозитории лежит `pnpm-lock.yaml` (`lockfileVersion: '9.0'`).
Поля `packageManager` в `package.json` нет, поэтому конкретную версию pnpm выбирает Vercel
по lockfile — цифру «pnpm 10.x» из ранних заметок ничто в репозитории не подтверждает.

```powershell
cd D:\Clode\POLsaas-booking\project

pnpm dev            # разработка
pnpm build          # сборка
pnpm start          # прод-сервер локально
pnpm typecheck      # tsc --noEmit
pnpm lint           # next lint
pnpm test           # vitest run — все unit-тесты
pnpm test:e2e       # playwright (нужен установленный chromium)
pnpm migrate        # применить миграции к БД
```

Состояние на момент передачи (проверено лично, не по памяти):

| Проверка | Результат |
|---|---|

| `pnpm build` | успешно, главная — статическая с `revalidate = 86_400` |

Отдельные скрипты аудита в `служебное/scripts/` (запускаются `node`; `link-audit` работает

## 12. Грабли проекта

1. **`corePlugins.preflight: false`.** Tailwind не сбрасывает стили браузера. Нативные
   `<button>` и `<input>` выглядят как в 90-х, если их не оформить. Именно так «поехали»
   страницы `/my/login` и форма в копии кабинета. Всегда проверяйте вид контролов глазами.
2. **Лендинг стилизуется предсобранным CSS.** `public/assets/detailing-scoped.css` содержит
   фиксированный набор классов под `.detailing-root`. Новый класс Tailwind там не появится.
   Варианты: использовать существующие классы, инлайн-стили, либо пересобрать этот файл.
3. **`rewrite` на пререндеренную страницу = ошибки гидрации.** Если middleware делает
   `rewrite` на статическую/ISR-страницу, браузер получает кэш HTML, а React — свежий
   RSC-payload: расхождение и полный ре-рендер (#418/#423). Решение — отдельный
   динамический маршрут-зеркало (`force-dynamic`), как сделано для копий.
4. **Vitest `include`** перечисляет папки явно (`общие/lib`, `главная`, `телеграмм-бот`,
   `app`, `служебное/tests/unit`). Тест, положенный в другое место, не запустится.
5. **Тест `env-example.test.ts`** падает, если код читает переменную окружения, которой нет
   в `.env.example`. Новая переменная → сразу строка в `.env.example`.
6. **Партиционированные таблицы.** `bookings` партиционирована по месяцам
   (`0006`, `0010`, `0014`). Массовые запросы и индексы — с оглядкой на это.
7. **ISR на витринах.** `revalidate` работает; правки в кабинете должны сбрасывать кэш
   конкретного пути (`revalidatePath`), иначе владелец не видит своих изменений.
8. **Прод обновляется только деплоем.** Пуш в GitHub ничего не деплоит: GitHub-интеграция
   не подключена, деплой идёт через CLI.
9. **Локальная сборка падает на очистке `.next`.** В песочнице агента `npx next build`
   завершается ошибкой `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]` — это не баг
   проекта, а защита от массового удаления, которая не даёт Next убрать старые чанки.
   Обход уже встроен в `next.config.mjs`: соберите с отдельной папкой
   `$env:NEXT_DIST_DIR='.next-check'; npx next build`. На Vercel значение игнорируется
   (там принудительно `.next`, потому что выставлен `VERCEL=1`).
   После такой сборки Next дописывает `.next-check/types/**/*.ts` в `tsconfig.json` —
   верните файл (`git checkout -- tsconfig.json`) и удалите `.next-check`, иначе попадёт в коммит.
10. **Токен Vercel живёт недолго.** `npx vercel whoami` может внезапно ответить
   `The specified token is not valid`. Деплой и `env ls` после этого не работают до
   `npx vercel login`. Проверяйте до того, как обещать деплой.
