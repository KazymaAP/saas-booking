## 1. Что это за проект

**«Запишись»** — SaaS: готовые сайты-визитки с онлайн-записью для малого бизнеса
(детейлинг, салоны красоты, стоматологии, фитнес, репетиторы, фотостудии, юристы,
ветклиники, клининг, ремонт техники — 10 ниш).

Две аудитории:

1. **Предприниматель** — покупает сайт: подписка 1 000 ₽/мес (домен сервиса) или
   2 500 ₽/мес (свой домен), разовый запуск 5 000 ₽, выкуп кода 5 000 ₽.
   Цены лежат в таблице `settings` (`tariffs`, `default_price`) и читаются через
   `getPricing()`; значения по умолчанию — в `общие/lib/legal.ts → DEFAULT_PRICING`.
2. **Партнёр** — продаёт те же сайты, получает 1 000 ₽/мес с подписки клиента или
   1 000 ₽ разово за продажу кода, либо 25 % от своей цены. Экономика зашита в
   `общие/lib/partners.ts → computeDeal()`.

Продажи идут через личный кабинет партнёра: партнёр создаёт счёт (`createCheckout`),
клиент открывает `/pay/[id]` и платит через ЮKassa. Публичной самостоятельной покупки нет.

Нюанс, который стоит знать сразу: вариантов счёта в коде три — `subscription_5000`,
`code_5000`, `custom`. Первый выставляет клиенту **5 000 ₽/мес**, хотя лендинг и оферта
говорят про 1 000 ₽/мес (наш домен) и 2 500 ₽/мес (свой домен). Разбор — раздел 7.2.

Прод: **https://www.zapishisya.ru** (основной домен). Репозиторий:
**https://github.com/KazymaAP/saas-booking**.

## 3. Запуск и проверки

Node 22.x (`package.json → engines`). В настройках проекта на Vercel стоит другая версия,
но `engines` её перекрывает — это видно в логе сборки 26.11.2026 дословно:

> `Warning: Due to "engines": { "node": "22.x" } in your package.json file, the Node.js`
> `Version defined in your Project Settings ("26.x") will not apply, Node.js Version "22.x"`
> `will be used instead.`

То есть сборка идёт на 22.x, как локально. Цифра в настройках (26.x) ни на что не влияет,
пока в `package.json` есть `engines`. Локальный `.vercel/project.json` при этом хранит
`nodeVersion: 24.x` — это снимок на момент `vercel link`, он устарел и не показателен.

Пакетный менеджер — **pnpm**: `vercel.json` задаёт `installCommand: pnpm install` и
`buildCommand: pnpm build`, в репозитории лежит `pnpm-lock.yaml` (`lockfileVersion: '9.0'`).
Поля `packageManager` в `package.json` нет, поэтому версию выбирает Vercel сам. В логе
26.11.2026 это сказано прямо: `Using pnpm@10.x based on project creation date`, дальше —
`Done in 1.1s using pnpm v10.28.0`. Значит на сборке **pnpm 10.28.0**; ранняя заметка
про «pnpm 10.x» была верной, а её удаление при перепроверке — ошибкой.

```powershell
cd D:\Clode\POLsaas-booking\project

pnpm dev            # разработка
pnpm build          # сборка
pnpm start          # прод-сервер локально
pnpm typecheck      # tsc --noEmit
pnpm lint           # next lint
pnpm test           # vitest run — все unit-тесты
pnpm test:e2e       # playwright (нужен установленный chromium)
pnpm migrate        # применить миграции к БД
```

### 5.12. 26.11.2026 — GitHub-интеграция включилась и сразу упала сборка

Пользователь прислал лог сборки Vercel без комментариев — как есть.

**Что изменилось:** сборка запущена **самим Vercel из GitHub**, а не через CLI:
`Cloning github.com/KazymaAP/saas-booking (Branch: master, Commit: ae13517)`. То есть
GitHub-интеграция, которой не было 25.11 (раздел 5.8), теперь подключена, и пуш в `master`
запускает деплой автоматически.

**На чём упало:**

```
Error occurred prerendering page "/test/ful/sts"
EnvError: Переменные окружения не настроены:
  - NEXT_PUBLIC_SUPABASE_URL: не задана
...
> Export encountered errors on following paths:
	/test/ful/sts/page: /test/ful/sts
Command failed with exit code 1
```

**Почему упало именно там.** `/test/ful/sts` объявлена с `revalidate = 600`, то есть
рендерится статически **на сборке**, а в рендере вызывает `loadServices()` → `adminClient()`.
`adminClient()` бросает `EnvError` **синхронно**, до первого сетевого запроса, а в коде
стоял `.catch()` на `Promise.all` — он такую ошибку не ловит. Комментарий в файле обещал
«сбой базы не роняет страницу», но обещание не выполнялось. Локально и при деплое через CLI
ошибка не проявлялась, потому что переменные были.

**Почему при CLI-деплое переменные были, а при сборке из GitHub — нет.** `.vercelignore`
не исключает `.env*`, поэтому `npx vercel --prod` отправлял на сборку локальные `.env`
и `.env.local` вместе с исходниками. Git-интеграция клонирует только то, что в git, а
`.env` в `.gitignore` — значит переменные должны приходить из настроек проекта Vercel,
а их там нет. **Все прежние деплои через CLI проходили за счёт загруженных локальных
файлов окружения, а не за счёт настроек проекта.**

**Что сделано:** `loadServices()` обёрнута в `try/catch` — при отсутствии переменных
возвращает пустой список, и оглавление показывает только статические разделы. Добавлен
тест `app/test/ful/sts/catalog.test.ts` (5 случаев, включая бросок `EnvError` и падение
запроса).

**Как проверено:** сборка запущена с **физически убранными** `.env` и `.env.local`
(переименованы на время, возвращены в `finally`) — exit 0, `/test/ful/sts` в таблице
маршрутов помечена `○` (static), ошибок в логе нет. То есть воспроизведено ровно условие
Vercel, и сборка проходит.

**Что осталось за владельцем:** прописать переменные окружения в проекте Vercel
**`servis`** (владелец подтвердил 26.11: проект на Vercel — `KazymaAP/servis`,
репозиторий — `KazymaAP/saas-booking`; это одна и та же пара, «другой проект» тут ни при чём).

### 5.14. 26.11.2026 — почему прод не обновлялся: разбор по API Vercel

Владелец вошёл в Vercel CLI (`npx vercel login` → «You are now signed in»), и появилась
возможность проверить настройки проекта не на глаз, а запросами к API. Картина оказалась
не той, что записана в 5.12.

**CLI «не авторизован» — ложная тревога.** `npx vercel whoami` возвращал `exit 1` без
вывода не из-за токена: `npx` пытался поставить свежий CLI и упирался в интерактивный
вопрос `Ok to proceed? (y)`, а в неинтерактивном режиме молча падал. Лечится явной
версией: `npx --yes vercel@67.0.0 whoami` → `kazymaap`.

**Что было в проекте `servis`:**

| Настройка | Было | Стало |
|---|---|---|
| Framework Preset | `Other` | `nextjs` |
| Output Directory | `dist` | пусто (`.next` из `vercel.json`) |
| Production Branch | `main` | `main` (сменить на `master` нельзя, см. ниже) |
| Переменные, Production | 16 штук, включая все 6 обязательных | +7 |
| Переменные, Preview | 1 (`ENCRYPTION_KEY`) | 13 |

Пресет `Other` и `dist` сборку не ломали: `vercel.json` в корне объявляет
`framework: nextjs`, `outputDirectory: .next`, `buildCommand: pnpm build` и перекрывает
настройки дашборда. Приведено к одному виду, чтобы дашборд не вводил в заблуждение.

**Причина падения из 5.12 — не та, что записана.** Переменные в Production **были**,
пустым был Preview. Пуш в `master` при production-ветке `main` — это деплой в Preview,
а не в Production: то есть даже если бы такой деплой создавался, он собирался бы без
переменных и падал на `NEXT_PUBLIC_SUPABASE_URL`.

**Главное: сейчас деплой из GitHub не создаётся.** В истории проекта все 40 последних
деплоев имеют источник `cli` и автора `kazymaap`; сборки с коммитом `ae13517` (та, чей лог
прислал владелец) среди них нет. Проверка боем: создание deploy hook на ветку `main`
вернуло `git_branch_not_found: Branch "main" not found in the connected Git repository`,
хотя ветка на GitHub есть (`git ls-remote` показывает и `main`, и `master`). Значит
GitHub-приложение Vercel не видит содержимое репозитория `KazymaAP/saas-booking`:
ветки не читаются, вебхуки не приходят. `vercel git connect` при этом отвечает
«already connected» — запись о привязке осталась, доступа за ней нет.

Расхождение, которое осталось необъяснённым: лог падения начинался с
`Cloning github.com/KazymaAP/saas-booking (Branch: master, Commit: ae13517)` и упоминал
Node `26.x`, то есть сборка была именно из GitHub и в проекте с другой версией Node.
Других проектов с этим репозиторием в команде нет (проверены все 11), у всех Node `24.x`.
Варианты: сборку удалили из истории, либо она шла в проекте, к которому у текущего токена
нет доступа. На выводы это не влияет — сейчас автодеплой не работает, это проверено.

production-ветка в Vercel — `main`. Ветки выровнены: `main` перемотана вперёд до

## 12. Грабли проекта

1. **`corePlugins.preflight: false`.** Tailwind не сбрасывает стили браузера. Нативные
   `<button>` и `<input>` выглядят как в 90-х, если их не оформить. Именно так «поехали»
   страницы `/my/login` и форма в копии кабинета. Всегда проверяйте вид контролов глазами.
2. **Лендинг стилизуется предсобранным CSS.** `public/assets/detailing-scoped.css` содержит
   фиксированный набор классов под `.detailing-root`. Новый класс Tailwind там не появится.
   Варианты: использовать существующие классы, инлайн-стили, либо пересобрать этот файл.
3. **`rewrite` на пререндеренную страницу = ошибки гидрации.** Если middleware делает
   `rewrite` на статическую/ISR-страницу, браузер получает кэш HTML, а React — свежий
   RSC-payload: расхождение и полный ре-рендер (#418/#423). Решение — отдельный
   динамический маршрут-зеркало (`force-dynamic`), как сделано для копий.
4. **Vitest `include`** перечисляет папки явно (`общие/lib`, `главная`, `телеграмм-бот`,
   `app`, `служебное/tests/unit`). Тест, положенный в другое место, не запустится.
5. **Тест `env-example.test.ts`** падает, если код читает переменную окружения, которой нет
   в `.env.example`. Новая переменная → сразу строка в `.env.example`.
6. **Партиционированные таблицы.** `bookings` партиционирована по месяцам
   (`0006`, `0010`, `0014`). Массовые запросы и индексы — с оглядкой на это.
7. **ISR на витринах.** `revalidate` работает; правки в кабинете должны сбрасывать кэш
   конкретного пути (`revalidatePath`), иначе владелец не видит своих изменений.
8. **Прод обновляется только через CLI — пуш не деплоит.** С 26.11 автодеплой из GitHub
   не создаётся: Vercel не видит содержимое репозитория (5.14, раздел 9 п. 7). Раньше это
   маскировалось дважды: `.vercelignore` не исключал `.env*` (CLI возил секреты с собой),
   а сборки из GitHub либо падали, либо не запускались. Проверка одной командой:
   `npx --yes vercel@67.0.0 project update servis --git-branch main -y` — если отвечает
   «Branch "main" not found», доступ к репозиторию потерян.
9. **Локальная сборка падает на очистке `.next`.** В песочнице агента `npx next build`
   завершается ошибкой `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]` — это не баг
   проекта, а защита от массового удаления, которая не даёт Next убрать старые чанки.
   Обход уже встроен в `next.config.mjs`: соберите с отдельной папкой
   `$env:NEXT_DIST_DIR='.next-check'; npx next build`. На Vercel значение игнорируется
   (там принудительно `.next`, потому что выставлен `VERCEL=1`).
   После такой сборки Next дописывает `.next-check/types/**/*.ts` в `tsconfig.json` —
   верните файл (`git checkout -- tsconfig.json`) и удалите `.next-check`, иначе попадёт в коммит.
10. **`npx vercel` без версии выглядит как истёкший токен.** `npx vercel whoami` может
   вернуть `exit 1` без вывода — это не токен, а вопрос «поставить свежий CLI? (y)»,
   на который в неинтерактивном режиме никто не отвечает. Всегда:
   `npx --yes vercel@67.0.0 …`. Настоящая потеря токена выглядит иначе — текстом
   `The specified token is not valid`; лечится `npx vercel login`.
11. **`try { adminClient() }` ловит не всё, если написано как `.catch()`.** `adminClient()`
   бросает `EnvError` синхронно, до первого запроса, поэтому `.catch()` на `Promise.all`
   такую ошибку не поймает и билд упадёт на предрендере. Если страница рендерится статически
   (`revalidate`, `generateStaticParams`) и читает базу — оборачивать в `try/catch` целиком.
   Реальный случай — `/test/ful/sts`, 25.11.2026 (раздел 5.12).
